## Working agreement — commits

- **Never run `git commit` (or `git push`) yourself.** The user commits manually.
- After each significant, reasonably large chunk of work, stop and propose a
  commit message for the current state of the working tree, so the user can
  commit it by hand. Do not continue to the next chunk until they have.
- Message style follows the existing history: conventional prefix
  (`feat:`, `fix:`, `docs:`, `refactor:`, …), short subject line, then a body
  listing the notable changes.
- No AI attribution in commit messages: never add `Co-Authored-By: Claude …`
  or any other "generated by" trailer.
- Commands must survive copy-paste from the terminal, which adds leading
  indentation to every copied line. So:
  - never use heredocs (`<<'EOF'` breaks when the terminator gets indented);
  - never split a command across lines;
  - write the full message to `.git/COMMIT_<n>.txt` (inside `.git/`, so it is
    never tracked) and give one short single-line command per step, e.g.
    `git add <files>` and `git commit -F .git/COMMIT_1.txt`;
  - also show the message text in the reply so the user can review it;
  - `git commit -F` does not delete the file, so finish with a separate
    single-line cleanup command: `rm .git/COMMIT_*.txt`.

## Project purpose

`uye-edge` is a **Dockerized NGINX edge API gateway** for the UYE platform.
It is the outermost network layer: it handles TLS termination, reverse-proxying,
rate limiting, compression, and security headers. It contains **no business logic**.

The platform upstream is the internal Go Gateway (`uye-gate`), which owns
session → JWT conversion and authorization. That service lives in a separate
repository and is referenced here only as an upstream target.

This repo is the **shared edge for multiple applications**. Base configuration
(`conf.d/`, `snippets/`, default servers) is owned here; each application gets its
own site file in `nginx/templates/sites/<app>.conf.template`, also kept in this
repo (see "Adding a new application"). Site configs are deliberately NOT kept in
the application repos: one nginx process serves every site, so a single broken
site fails `nginx -t` for all of them, and conflicts (`server_name`, upstream and
zone names) are only detectable when all sites are validated together.

```
Browser  ──HTTPS──▶  uye-edge (this repo)  ──HTTP──▶  Go Gateway  ──▶  Microservices
```

---

## Strict scope boundary

- NGINX handles: TLS, routing, rate limiting, compression, access logging, security headers, health checks.
- NGINX does NOT handle: authentication, authorization, session management, JWT, business routing rules.
- Never add business logic, auth checks, or Lua scripts to this repo.
- Never add application-level services (databases, caches, app servers) to docker-compose.yml.

### Environment naming

- **local** — a developer machine (`docker-compose.local.yml`, `.env.local`, `local/`,
  `certs/local/`).
- **dev** — reserved for a future shared dev server. Do not use `dev` for local files.

Only `.env.example` is tracked. Every other `.env*` file is gitignored and generated
or created by hand on the target machine.

## Configuration templating — critical mechanism

The official `nginx:1.27-alpine` Docker image includes
`/docker-entrypoint.d/20-envsubst-on-templates.sh`.
At container startup, **before nginx launches**, this script:

1. Reads every `*.template` file from `/etc/nginx/templates/`.
2. Runs `envsubst` against the process environment.
3. Writes the result to `$NGINX_ENVSUBST_OUTPUT_DIR/<relative-path-without-.template>`.
   The Dockerfile sets `NGINX_ENVSUBST_OUTPUT_DIR=/etc/nginx/generated`; subdirectories
   (e.g. `templates/sites/`) are preserved.

**Consequences:**
- Files in `nginx/templates/` are NOT valid nginx config on their own; they are text templates.
- The final nginx config exists only inside the running container at `/etc/nginx/generated/`.
- Output goes to `generated/`, not `conf.d/`, because the container root filesystem is
  read-only (`read_only: true`) and local compose bind-mounts `conf.d/` as `:ro`. If the output dir
  is not writable, the entrypoint silently skips rendering and nginx fails on the missing
  includes. In compose, `/etc/nginx/generated` is a root-owned tmpfs (the entrypoint runs
  as root without `CAP_DAC_OVERRIDE`, so it cannot write into a uid-101-owned tmpfs).
- The same rule applies to every writable tmpfs the nginx master touches
  (`/var/cache/nginx`, `/var/run`): they must be root-owned, NOT `uid=101`. The
  master creates the `*_temp` subdirs itself and chowns them to the worker user
  via `CAP_CHOWN`; workers still run as `nginx`.
- Templates are rendered only at container start. `nginx -s reload` picks up edits to
  static files (`conf.d/`, `snippets/`, `nginx.conf`) but NOT template edits — restart
  the container for those.
- To validate a template locally, set env vars and run `envsubst < template > /tmp/out && nginx -t -c /tmp/out`.
- `nginx.conf` itself is NOT processed by envsubst. It contains only static directives.

### envsubst variable collision risk

`envsubst` substitutes ALL environment variables present in the process.
Nginx variables (`$host`, `$uri`, `$remote_addr`, `$scheme`, `$request_uri`, etc.)
use lowercase names. Container env vars in this project use uppercase (`NGINX_*`).
These do NOT collide — lowercase nginx variables are safe from substitution.

**Do not** name env vars with lowercase or mixed-case names that match nginx built-in
variables (e.g. `host`, `scheme`, `uri`). This would cause substitution corruption.

## Environment variables reference

All variables must be present in the environment when the container starts.
Missing variables cause `envsubst` to silently produce empty strings, which will
fail nginx config validation (`nginx -t`).

| Variable | Format | Example | Notes |
|---|---|---|---|
| `NGINX_DOMAIN` | hostname | `api.example.com` | Used as `server_name` in both server blocks, and in default cert paths |
| `CERTBOT_EMAIL` | email | `ops@example.com` | Used only by `certbot` profile |
| `NGINX_SSL_CERT_PATH` | absolute path | `/etc/nginx/ssl/live/api.example.com/fullchain.pem` | Must exist inside container at runtime |
| `NGINX_SSL_KEY_PATH` | absolute path | `/etc/nginx/ssl/live/api.example.com/privkey.pem` | Must exist inside container at runtime |
| `NGINX_SSL_CHAIN_PATH` | absolute path | `/etc/nginx/ssl/live/api.example.com/chain.pem` | Required for OCSP stapling (`ssl_trusted_certificate`) |
| `NGINX_UPSTREAM_HOST` | hostname/IP | `go-gateway` | Docker service name or external hostname |
| `NGINX_UPSTREAM_PORT` | port | `8080` | Port the Go Gateway listens on |
| `NGINX_LB_ALGORITHM` | nginx directive or empty | `least_conn;` | **Must include the trailing semicolon**, or be empty for round-robin. See below. |
| `NGINX_RATE_LIMIT_RATE` | nginx rate | `100r/m` | `limit_req_zone` rate for `api_per_ip` zone |
| `NGINX_RATE_LIMIT_BURST` | integer | `20` | `limit_req burst=` value for `/api/` |
| `NGINX_RATE_LIMIT_AUTH_RATE` | nginx rate | `10r/m` | Rate for `auth` zone |
| `NGINX_RATE_LIMIT_AUTH_BURST` | integer | `5` | Burst for `/api/auth/` |
| `NGINX_RATE_LIMIT_GENERAL_RATE` | nginx rate | `200r/m` | Rate for `general` zone |
| `NGINX_RATE_LIMIT_GENERAL_BURST` | integer | `50` | Burst for catch-all `/` |
| `NGINX_CONN_LIMIT_PER_IP` | integer | `20` | `limit_conn conn_per_ip` value in all location blocks |
| `GO_GATEWAY_IMAGE` | Docker image | `nginx:alpine` | Only used by `go-gateway` service under `stub` profile |

### NGINX_LB_ALGORITHM special handling

This variable is injected as a raw line inside the `upstream go_gateway { }` block.
The value **must be a complete nginx directive including the semicolon**, or empty.

```
NGINX_LB_ALGORITHM=            # round-robin (default, no directive needed)
NGINX_LB_ALGORITHM=least_conn; # least connections
NGINX_LB_ALGORITHM=ip_hash;    # IP hash (session affinity)
```

If you set it to `least_conn` without the semicolon, nginx config validation will fail.

## nginx.conf — key decisions

- `worker_processes auto` — nginx auto-detects CPU count; do not hardcode.
- `worker_rlimit_nofile 65535` — must match or be less than the container's `ulimit -n`.
- `worker_connections 4096` — max simultaneous connections per worker. Total capacity = workers × 4096.
- `client_max_body_size 10m` — hardcoded here, not env-templated. Change in `nginx.conf` if uploads require larger bodies.
- Include order: static conf.d/ files first (`logging`, `gzip`, `security`, `ssl-params`, `proxy-params`), then templated files (`rate-limit`, `upstream`, `http-server`, `https-server`), then `generated/sites/*.conf`, then `local-sites/*.conf` (empty outside local). The order within the http block matters only for inheritance; nginx validates all references after full parsing.

## conf.d/logging.conf — nuances

- Log paths are symlinks in the base image (`access.log` → `/dev/stdout`,
  `error.log` → `/dev/stderr`), so all logs go to the Docker logging driver.
  There is deliberately **no** log volume — a volume over `/var/log/nginx` would
  only persist the symlinks. Collect logs from the container (`docker logs`,
  Loki/Alloy `loki.source.docker`, a Docker logging driver). If file logs are ever
  needed, point `access_log` at a real file AND add log rotation.

- Uses `log_format json_combined escape=json` — the `escape=json` flag properly escapes special characters (quotes, backslashes, control chars) in variable values. Without it, user-supplied input in `$http_user_agent` or `$args` can break JSON structure.
- `buffer=32k flush=5s` on `access_log` — log lines are buffered in memory and flushed every 5 seconds. This reduces I/O at high RPS but means up to 5 seconds of logs can be lost on hard crash. Acceptable for an edge gateway.
- `$upstream_response_time` will contain `-` for requests served directly by nginx (e.g. `/healthz`, `/nginx-status`). This is normal and must be handled in any log processing pipeline.
- `$request_id` is a 32-char hex string generated by nginx (built-in since nginx 1.11.0). It is unique per request and not related to any client header.

## conf.d/security.conf — nuances

- `$block_ua` map: evaluated for every request in the HTTPS server block via `if ($block_ua)`. The map uses case-insensitive regex (`~*`). Empty user-agent (`""`) returns `1` (blocked). The Go HTTP client exception (`~*go-http-client/1\.1$`) prevents blocking internal Go services that call back through the edge.
- `$invalid_method` map: blocks `TRACE` and `TRACK` (used in XST attacks). `DELETE` and `PATCH` are explicitly allowed (`0`). All others default to `0` (allowed). Add more methods here if needed.
- `proxy_max_temp_file_size 1024m` is placed here for grouping but is an `http`-context directive that controls how much response body nginx can spool to disk when upstream sends faster than the client reads. This protects upstream from being held open by slow clients.
- The `geo $blocked_ip` block is commented out. To activate IP-based blocking: uncomment the geo block, populate the CIDR ranges, then add `if ($blocked_ip) { return 403; }` to `snippets/guard-rails.conf` (applies to every site).

## conf.d/ssl-params.conf — nuances

- `ssl_prefer_server_ciphers off` — for TLS 1.3 this is meaningless (client always chooses); for TLS 1.2 this lets the client pick from the allowed list rather than forcing server order. Mozilla Intermediate profile recommends `off`.
- `ssl_session_tickets off` — session tickets compromise forward secrecy if the ticket key leaks. Disabled in favor of session cache.
- `ssl_session_cache shared:SSL:50m` — 50 MB shared across all workers. 1 MB ≈ 4000 sessions. 50 MB handles ~200k concurrent sessions.
- OCSP stapling requires `ssl_trusted_certificate` (the CA chain) to be set in the server block — this is why `NGINX_SSL_CHAIN_PATH` is a required variable and referenced in `https-server.conf.template` and `sites/uye.conf.template`. Every site needs its own chain path.
- `resolver 1.1.1.1 8.8.8.8` — used for OCSP stapling DNS resolution. In Kubernetes or air-gapped environments, replace with the cluster DNS resolver.
- DH params are commented out. If re-enabled, generate with `openssl dhparam -out /etc/nginx/ssl/dhparam.pem 2048` (takes ~30s). Mount the file into the container.

## conf.d/proxy-params.conf — nuances

- `proxy_http_version 1.1` + `proxy_set_header Connection ""` — **both are required** for upstream keepalive to function. Without these, nginx uses HTTP/1.0, which does not support persistent connections, making the `keepalive 32` directive in the upstream block useless.
- `proxy_set_header Connection ""` clears the `Connection` header from the client (which might say `close` or list hop-by-hop headers). Clearing it allows keepalive to be negotiated between nginx and the upstream.
- `proxy_hide_header X-Powered-By` and `proxy_hide_header Server` — prevents the Go Gateway from leaking its technology stack in responses.
- `proxy_next_upstream error timeout` — retries the next upstream server ONLY on connection-level failures. Intentionally does NOT include `http_500`, `http_502`, etc. Retrying on 500 would cause side effects (duplicate writes) on non-idempotent requests. If Go Gateway returns a 5xx, that error is passed to the client.
- `proxy_next_upstream_tries 2` — tries at most 2 servers total (1 original + 1 retry). With a single upstream server, this has no effect but is ready for multi-instance deployments.

### proxy_set_header inheritance warning

`proxy_set_header` directives set at `http` context (in proxy-params.conf) are
inherited by all `server` and `location` blocks **only if** that block does not
define ANY `proxy_set_header` of its own. If you add a `proxy_set_header` inside
a `location` block in any site template, the http-level headers will
be silently dropped for that location. To avoid this, never add `proxy_set_header`
in individual location blocks; make all header changes in `proxy-params.conf`.

## nginx/templates/upstream.conf.template — nuances

- The upstream name `go_gateway` is hardcoded. All `proxy_pass http://go_gateway;` directives (currently in `sites/uye.conf.template`) reference this name. Do not rename it without updating every site that uses it.
- Upstreams for other applications are declared in their own site file, not here (see "Adding a new application").
- `max_fails=3 fail_timeout=30s` — nginx marks a server as unavailable after 3 consecutive connection failures within 30s. It re-tests the server after 30s. This is passive health checking (nginx does not actively probe).
- Active health checks (`health_check` directive) require `nginx-plus`. The open-source version relies on this passive mechanism. Combine with a monitoring alert on `upstream_status` in access logs to detect degradation.
- `keepalive 32` sets the pool size of idle keepalive connections. It does not limit total connections to the upstream. Tune this to match the Go Gateway's `max_idle_conns` setting.

## Default servers — http-server / https-server templates

- `http-server.conf.template` is the `default_server` on :80 for **all** hosts: ACME
  challenge, `/healthz`, `/nginx-status`, and a 301 to HTTPS. Sites do not define
  their own :80 server.
- `https-server.conf.template` is the `default_server` on :443. It uses the platform
  certificate (`NGINX_SSL_*`), serves only `/healthz` and `/nginx-status`, and returns
  `444` (close connection) for everything else, so an unknown `Host` never reaches an
  application upstream.

## nginx/templates/sites/uye.conf.template — nuances

### Location matching order and priority

Three prefix location blocks exist:
```
location ^~ /api/auth/   # highest priority among prefixes (^~ modifier)
location /api/           # longer prefix, wins over /
location /               # catch-all
```

The `^~` modifier on `/api/auth/` ensures regex location blocks (like the
`.git/.env` regex) do not intercept auth routes. For prefix matching without `^~`,
nginx checks regex locations after finding the longest prefix match. With `^~`,
if this prefix matches, nginx stops and uses it — no regex check.

Any new specific prefix routes (e.g., `/api/admin/`) should be added with `^~`
if they must not be intercepted by regex blocks. Add them BEFORE `/api/` in the
template to keep the intent clear, even though nginx would find the longer match
regardless of order.

### Security headers and add_header inheritance

Security headers come from `snippets/security-headers.conf`, included at server level.
`add_header` at the `server` level is inherited by `location` blocks ONLY if
that location block has zero `add_header` directives. The named error locations
(`@rate_limited`, `@upstream_error`, `@bad_request`) do contain `add_header`
(e.g. `Retry-After` in `@rate_limited`), which means they do NOT inherit the
HSTS and other security headers from the server block. This is intentional for
error responses — adding HSTS to a 429 JSON body is not needed. If you add
`add_header` to a regular location block, also `include /etc/nginx/snippets/security-headers.conf;`
inside that location.

### HTTP/2

`http2 on;` (in `snippets/tls.conf`) is the nginx >= 1.25.1 syntax. The old `listen 443 ssl http2;` syntax
is deprecated in nginx 1.27. Do not mix the two. The base image is `nginx:1.27-alpine`.

### /healthz

Returns a static JSON `{"status":"ok","service":"uye-edge"}` from nginx directly —
it does NOT proxy to the Go Gateway. This ensures the health check reflects nginx
availability, not upstream availability. Defined in `snippets/health.conf` and
available on HTTP (port 80) and on HTTPS for every host, including unknown ones.

### /nginx-status

Exposes `stub_status` data. Access is restricted to RFC-1918 ranges and localhost.
The `nginx-exporter` container scrapes this endpoint at `http://nginx/nginx-status`
over the internal `edge` Docker network (served by the :80 default server).

## Docker Compose profiles

| Profile | Services activated | When to use |
|---|---|---|
| _(none)_ | `nginx` only | CI, image build checks |
| `stub` | `nginx` + `go-gateway` (stub) | Integration testing without the real Go Gateway |
| `certbot` | `nginx` + `certbot` | Initial cert issuance; cert renewal via `certbot-renew.sh` |
| `observability` | `nginx` + `nginx-exporter` | When Prometheus scraping is needed |

**Important:** nginx declares `depends_on: go-gateway` with `required: false`,
because `go-gateway` exists only under the `stub` profile. Without `required: false`
compose refuses to start (`depends on undefined service "go-gateway"`).
Compose will start nginx without the stub, but nginx itself still resolves
`NGINX_UPSTREAM_HOST` at startup and exits with `host not found in upstream`
if it is not reachable. In production, the real Go Gateway runs in a separate
stack and joins the network externally. The network has a fixed name, `uye-edge`
(`networks.edge.name`), so other stacks reference it as
`networks: { uye-edge: { external: true } }` regardless of the compose project name.

The compose project name is pinned with top-level `name: infra-edge`: the deployer
(`--project-name infra-edge`), `certbot-renew.sh` (`-f docker-compose.yml`) and manual
commands must address the same project, otherwise compose tries to create a second
`uye-edge` container and fails on the `container_name` conflict.

## Local development workflow

```bash
# 1. One-time setup: .env.local (from .env.example) + certs/local/*
make init

# 2. Start the local stack (nginx + stubs + nginx-exporter), wait until healthy
make up

# 3. Test
curl --cacert certs/local/ca.pem https://localhost/healthz
curl --cacert certs/local/ca.pem https://localhost/api/anything

# 4. Validate + hot-reload static config (conf.d/, snippets/, nginx.conf)
make reload

# 5. Template edits need a restart (templates are rendered only at startup)
make restart
```

`make help` lists all targets. The Makefile runs compose as
`docker compose --env-file .env.local -f docker-compose.yml -f docker-compose.local.yml`;
`--env-file` makes compose interpolation (`${CERTBOT_EMAIL}`, `${GO_GATEWAY_IMAGE}`)
read `.env.local` instead of the production `.env`.

`.env.local` is generated by `scripts/init-local-env.sh`: it copies `.env.example`
and replaces only the values listed in its `OVERRIDES` block (localhost domain, local
cert paths, stub upstream port, 10× relaxed rate limits). Every override key must exist
in `.env.example`, otherwise the script fails. An existing `.env.local` is kept;
regenerate with `scripts/init-local-env.sh --force` after `.env.example` changes.

Local compose overrides (`docker-compose.local.yml`):
- Bind-mounts `nginx/nginx.conf`, `nginx/conf.d/`, `nginx/snippets/`, `nginx/templates/` so config edits take effect without rebuilding the image (`nginx -s reload` for static files, container restart for templates).
- Uses `.env.local` instead of `.env` via `env_file: !override` — a plain list would
  be merged with the base `.env`.
- Activates `go-gateway` and `nginx-exporter` without requiring profile flags via
  `profiles: !reset []` — a plain `profiles: []` does not clear the base profile.
- The `!override` / `!reset` tags require Docker Compose >= 2.24.
- Mounts `./certs/local` as `/etc/nginx/ssl` (read-only).
- Mounts `local/sites/` as `/etc/nginx/local-sites/` and starts `demo-stub`.

### Local certificates

`scripts/generate-local-certs.sh` (`make certs`, `make certs-force`) writes
`certs/local/{cert,key,ca}.pem` for every host in its `HOSTS` list
(`localhost demo.localhost 127.0.0.1 ::1`). With `mkcert` installed the cert is
signed by the mkcert CA (`ca.pem` = mkcert root) and browsers trust it after
`mkcert -install`; otherwise it is self-signed (`ca.pem` = the cert). Clients
use `--cacert certs/local/ca.pem` instead of `-k`. HSTS is sent for `localhost`,
so a browser that once saw an untrusted cert there may need its HSTS entry cleared.

### Local-only sites (demo.localhost)

`local/sites/*.conf` are **static** nginx files (no envsubst) mounted into
`/etc/nginx/local-sites/`; `nginx.conf` includes `/etc/nginx/local-sites/*.conf`
last. The directory exists but is empty in the production image, so the glob
matches nothing there. They are not templates under `nginx/templates/sites/`
because a single-file bind mount cannot be created inside the `:ro` templates
mount. `demo.localhost` exercises the multi-site setup: own `demo_backend`
upstream and `demo_general` zone, shared snippets, Host/SNI isolation. New local
hostnames must also be added to `HOSTS` in `generate-local-certs.sh`.

Single-file bind mounts (`local/*-stub.conf`) pin the file's inode: editors that
save by replacing the file are not seen by the running container — recreate it
(`docker compose ... up -d --force-recreate <service>`).

## Checks and linters

| Command | What it does |
|---|---|
| `make hooks` | One-time: install pre-commit (on commit) and pre-push hooks |
| `make lint` | `pre-commit run --all-files`: whitespace/EOF, JSON/YAML syntax, shellcheck, hadolint, yamllint, dotenv-linter, env-var sync, compose config |
| `make test-config` | `check-env-vars.sh` + `compose-config.sh` + `nginx-t.sh` (Docker only, no running stack needed) |
| `make smoke` | hurl smoke tests against the running local stack |
| `make test` | `test-config` → `up` (waits for healthy) → `smoke` |

`tests/config/nginx-t.sh` builds the image and, for `.env.example` (production shape)
and a freshly generated local env, runs the image's envsubst step, `nginx -t`, then
gixy (static security analysis) on the rendered config. Dummy certs are mounted at
the paths from each env file and upstream hosts are mapped to 127.0.0.1 with
`--add-host`, because nginx resolves upstreams at config-test time. The expected
`"ssl_stapling" ignored` warnings are filtered out.

gixy skips live in `GIXY_SKIPS` in `nginx-t.sh`, each with a reason. Do not add a skip
without one; fix the config instead when the finding is real.

`check-env-vars.sh` fails when a template uses a `${VAR}` that `.env.example` lacks,
or `.env.example` defines a variable used nowhere (templates or compose interpolation).

The pre-push hook runs `nginx-t.sh` only when nginx/env/test files changed.

### CI

`.github/workflows/ci.yml` runs on every PR and on push to `main`, using the same
entry points as local development — keep it that way (CI logic goes into the
Makefile/scripts, not into the workflow):

| Job | Runs |
|---|---|
| `lint` | `pre-commit run --all-files` (commit-stage hooks, incl. actionlint) |
| `config` | `make test-config` |
| `smoke` | `make init` → `make up` → `make smoke`; compose logs on failure; `make down` |
| `publish` | push to `main` only, after the three above: Buildah build → push `ghcr.io/uye-ltd/infra-edge:{latest,<sha>}` → `cosign sign` by digest |

The runner has no mkcert, so `make init` produces the openssl self-signed cert.

`publish` runs on the self-hosted infra-runner (`[self-hosted, linux, x64]`): there is
no Docker daemon, so it builds with Buildah (`--isolation=chroot`), the same steps as
infra-vault. The signing identity is this workflow file
(`.../infra-edge/.github/workflows/ci.yml@refs/heads/main`) and the deployer checks it
by **exact** match (`.infra-runner.plugin`): renaming `ci.yml` or moving the job to another
workflow breaks deploys until `PLUGIN_CERT_IDENTITY` is updated. `lint`/`config`/`smoke`
stay on GitHub-hosted runners — they need Docker.

### Smoke tests (hurl)

`make smoke` runs the `smoke` service (`docker-compose.local.yml`, profile `test`)
on the `edge` network: `tests/smoke/run.sh` routes every local hostname to the
`nginx` service with `--connect-to` and trusts `certs/local/ca.pem`, so TLS/SNI
behave as from a browser. Coverage: health on :80/:443, 80→443 redirect, ACME
webroot, stub_status, security headers per site, routing per site and X-Request-ID
propagation, method/UA/sensitive-path guard rails, JSON 429 with `Retry-After`,
and — with curl, since hurl cannot assert "no response" — 444 for unknown Host/SNI.

- Files run sequentially in name order (`--jobs 1`); `zz-rate-limit.hurl` must stay
  last, it exhausts the `/api/auth/` bucket of the runner's IP for ~30 s.
- The stubs echo `host`, `path` and `request_id`; assertions rely on these fields.
- Stub configs are single-file bind mounts: after editing one, recreate the stub
  container (see "Local-only sites"), otherwise tests see the old response.
- **Every new site or route gets hurl tests** (at least: routing to its upstream,
  security headers, a guard-rail check). A local site for testing goes to
  `local/sites/` and its hostname to `HOSTS` in `generate-local-certs.sh` and to
  `--connect-to` in `run.sh`.

## Production workflow

Production runs on the infra-runner host, checkout `/home/ghrunner/infra-edge`, deployed
by the infra-runner **deployer** as a plugin (see infra-runner `deployer/PLUGINS.md`).
Step-by-step server setup is in README → "Production deploy (infra-runner)".

### How a deploy happens

```
push to main → ci.yml: lint, config, smoke → publish (build, push, cosign sign)
  → deployer (every POLL_INTERVAL): pull ghcr.io/uye-ltd/infra-edge:latest
      → new digest? → cosign verify (identity = ci.yml@refs/heads/main)
      → docker compose --project-name infra-edge --project-directory /workspace-edge up -d --no-deps nginx
      → scripts/wait-healthy.sh (on_update, blocking)
```

- `docker-compose.infra-runner.yml` is appended to `COMPOSE_FILE` in infra-runner's
  `.env` (with `EDGE_COMPOSE_DIR=/home/ghrunner/infra-edge`); it mounts the checkout at
  `/workspace-edge:ro` and the descriptor at `/plugins/infra-edge.plugin`.
- compose runs **inside the deployer container**, so relative bind mounts in
  `docker-compose.yml` would resolve to container paths. Production nginx uses only
  named volumes and `env_file: .env` — keep it that way (local bind mounts belong in
  `docker-compose.local.yml`).
- The deployer's socket proxy disables EXEC: post-deploy hooks may only use `docker inspect`
  / other non-exec API calls. `wait-healthy.sh` polls `.State.Health` of `uye-edge`
  (`WAIT_HEALTHY_TIMEOUT`, default 120 s).
- **Image-only GitOps.** Only what is inside the image deploys automatically (`nginx/**`,
  `Dockerfile`). `docker-compose.yml`, the descriptor and the hook script are read from the
  server checkout, kept current by a `git pull --ff-only` cron. Server `.env` edits need a
  manual `docker compose up -d nginx`.
- No automatic rollback: a failed verify / `compose up` / health wait sets the deployer's
  `/health` to 503 and leaves the new container in place. Roll back by reverting on `main`.
- The GHCR package must be public (deployer uses a GitHub App token, which cannot read GHCR).

### First certificate issuance

nginx cannot start without the certificate files, and the image is prebuilt, so the first
certificate is issued with certbot in standalone mode before nginx exists:

```bash
cp .env.example .env && nano .env
docker compose --profile certbot run --rm -p 80:80 certbot certonly --standalone --email <email> --agree-tos --no-eff-email -d <domain> -d www.<domain>
docker compose pull nginx && docker compose up -d nginx
```

Later certificates (renewals, additional domains) use the webroot flow through the running
:80 default server.

### Certificate renewal

```bash
# cron as ghrunner (see scripts/certbot-renew.sh)
0 3 * * * /home/ghrunner/infra-edge/scripts/certbot-renew.sh >> /home/ghrunner/certbot-renew.log 2>&1
```

`certbot-renew.sh` overrides the certbot container command to `renew` (not `certonly`).
After renewal it runs `nginx -s reload` to pick up the new certificate without downtime.

### Cert volume layout (inside container)

```
/etc/nginx/ssl/                              ← certbot_certs volume (mounted :ro in nginx)
└── live/
    └── <NGINX_DOMAIN>/
        ├── fullchain.pem                    ← ssl_certificate
        ├── privkey.pem                      ← ssl_certificate_key
        └── chain.pem                        ← ssl_trusted_certificate (OCSP)
```

`certbot_certs` maps to `/etc/letsencrypt` inside the certbot container, where
Let's Encrypt stores `live/`, `archive/`, `renewal/` directories. Nginx sees it
read-only at `/etc/nginx/ssl`.

## Prometheus / observability

### Local monitoring stack

`make up-monitoring` starts the `monitoring` profile from `docker-compose.local.yml`:

| Service | URL | Role |
|---|---|---|
| `prometheus` | http://localhost:9090 | scrapes `nginx-exporter:9113` |
| `loki` | internal `:3100` | stores access-log lines |
| `alloy` | — | reads `uye-edge` container stdout via the Docker socket → Loki |
| `grafana` | http://localhost:3000 | anonymous admin; home dashboard "uye-edge (local)" |

- The nginx image symlinks `/var/log/nginx/access.log` → stdout, so Alloy collects
  logs through the Docker API (`loki.source.docker`), not from files.
- Alloy promotes `status`, `method`, `host` (from `http_host`) to Loki labels; every
  other field is read with `| json` in LogQL. Keep labels low-cardinality — never
  promote `uri`, `request_id`, `remote_addr`.
- Dashboard JSON lives in `local/observability/grafana/dashboards/edge.json` and is
  provisioned read-from-file; UI edits are allowed but must be exported back into the
  file to persist. Metrics from stub_status are global (no per-host split); per-host
  and latency panels come from Loki.
- Image versions are pinned; data lives in `prometheus_data`, `loki_data`,
  `grafana_data` volumes (`make down` keeps them; `docker volume rm` to reset).
- This stack is local-only. Production observability is out of scope for this repo.

### Production exporter

```
nginx-exporter  →  GET http://nginx/nginx-status  →  parses stub_status
                ←  exposes :9113/metrics          ←  Prometheus scrapes this
```

Key metrics from nginx-prometheus-exporter:
- `nginx_connections_active` — currently active connections
- `nginx_connections_reading` / `_writing` / `_waiting`
- `nginx_http_requests_total` — total requests handled

For richer metrics (per-route latencies, 4xx/5xx rates, upstream response times),
ship JSON access logs to a log aggregation stack (Loki + Grafana, or ELK).
The `upstream_response_time` and `status` fields in the JSON log are the primary
SLI data sources for Go Gateway latency and error rate.

`X-Request-ID` is the distributed trace carrier. It is:
1. Generated by nginx (`$request_id`, 32-char hex, unique per request).
2. Forwarded to Go Gateway in `X-Request-ID` proxy header (set in proxy-params.conf).
3. Returned to the client in the `X-Request-ID` response header (set in `snippets/security-headers.conf`).
4. Logged in every access log line as `"request_id":"..."`.

## Adding a new application

Each application served by this edge gets one file: `nginx/templates/sites/<app>.conf.template`.
The application team opens a PR against this repo; the edge owner reviews it.

1. Copy `nginx/examples/app.conf.template` to `nginx/templates/sites/<app>.conf.template`
   and replace `<app>` / `<APP>`.
2. Naming conventions (all sites share one `http` context):
   - nginx names (`upstream`, `limit_req_zone`, `map` variables) are prefixed `<app>_`.
   - env vars are prefixed `APP_<APP>_` (uppercase — see envsubst collision risk).
   - `server_name` must be unique across all sites; only the default servers use `default_server`.
3. The site file contains the app's `upstream`, its `limit_req_zone`s, and a single
   `server` block that includes `snippets/tls.conf`, `security-headers.conf`,
   `guard-rails.conf`, `health.conf` and `error-pages.conf`. The shared
   `conn_per_ip` zone and `NGINX_CONN_LIMIT_PER_IP` are reused.
4. Add every new `APP_<APP>_*` variable to `.env.example`; if the local value must
   differ, add it to the `OVERRIDES` block in `scripts/init-local-env.sh`. A missing
   variable renders as an empty string and fails `nginx -t` for **all** sites.
5. Issue a certificate for the new domain (certbot `certonly --webroot -d <domain>`;
   the :80 default server already serves the ACME webroot for any host).
6. Rebuild the image (or `make restart` locally) and run `make test-config`.
   Add hurl smoke tests for the site in `tests/smoke/` (see "Smoke tests").
7. Recommended: a `CODEOWNERS` entry `nginx/templates/sites/<app>.conf.template @<app-team> @<edge-owner>`.

If all applications sit behind `uye-gate`, per-app routing belongs in `uye-gate`; the
site file then only needs the domain, certificate and `proxy_pass http://go_gateway;`.

## Adding a new route or upstream

1. If the route has different rate limit requirements, add a new `limit_req_zone`
   in `nginx/templates/rate-limit.conf.template` with a new env var, and add the
   var to `.env.example` (plus a local override in `scripts/init-local-env.sh` if needed).

2. Add the `location` block to the site's template in `nginx/templates/sites/`.
   - Use `^~` prefix modifier if the route must not be intercepted by regex blocks.
   - Include `limit_req`, `limit_conn`, and `proxy_pass` — do NOT add `proxy_set_header`
     (see inheritance warning above).
   - Place more specific prefixes above less specific ones for clarity, even though
     nginx uses longest-match (not declaration order) for prefix locations.

3. If routing to a different upstream (not `go_gateway`), declare a new `<app>_`-prefixed
   `upstream` block in the site's own template and reference it in the location's `proxy_pass`.

4. Rebuild the image, or `make restart` locally (templates are rendered only at startup).
   In production the change ships with the next image: merge to `main` → `publish` → deployer.

## Adding configuration to conf.d/ vs snippets/ vs templates/

**Use `snippets/` (static) when:** the directive belongs at `server`/`location`
level and should be shared by several sites (headers, guard rails, error pages).

**Use `conf.d/` (static) when:** the directive is `http`-level and has no runtime-variable parts —
it is the same in dev, staging, and production (e.g. TLS cipher list, gzip MIME types,
log format, proxy buffer sizes).

**Use `templates/` (envsubst) when:** the directive contains values that differ
between environments or deployments (e.g. domain name, upstream host/port,
rate limit values, cert paths).

Do not introduce env vars into static conf.d/ or snippets/ files. They will not be substituted
and nginx will reject the config with a syntax error.

## Known limitations and deliberate omissions

- **Brotli compression** is not available in `nginx:1.27-alpine`. The standard
  nginx binary does not include the `ngx_brotli` module. To add it, switch the
  base image to `fholzer/nginx-brotli` and add a `brotli.conf` in `conf.d/`.

- **Active health checks** (probing upstream on a schedule) require nginx Plus.
  The open-source build uses passive health checks only (`max_fails` / `fail_timeout`
  in the upstream server directive).

- **DH parameters** for DHE cipher suites are commented out. DHE is included in
  the cipher list but effectively unused without `ssl_dhparam`. To enable it:
  generate `dhparam.pem`, mount it into the container, and uncomment the directive
  in `ssl-params.conf`.

- **Caching** is not configured. For API responses, caching is intentionally omitted
  because the Go Gateway owns cache invalidation logic. If edge caching for static
  assets is needed in future, add a `proxy_cache_path` directive and a `location`
  block with `proxy_cache`.

- **WAF / ModSecurity** is not included. The scanner-UA blocking and method filtering
  in `security.conf` are lightweight guards, not a full WAF. For ModSecurity, use
  the `owasp/modsecurity-crs:nginx-alpine` base image.

- **Multiple domains / SAN** are not explicitly configured. The `server_name` directive
  uses `${NGINX_DOMAIN} www.${NGINX_DOMAIN}`. For additional domains, either add
  them to the template as additional env vars or run separate nginx instances.
